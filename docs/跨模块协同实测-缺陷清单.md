## 0. 为什么单测全绿、协同仍然断裂

`coherence_audit.py`（门禁第 9 步）查的是"函数有没有调用方"，判据是**源码里出现过**。
它答不了更要命的问题：

**这次分析到底走了哪条路？**

静态看 `pipeline.py` 引用了 18 个模块，但这 18 个里有一半只在某个分支生效；
另外 46 个 lib 模块，有的一辈子没进过 `analyze` 的调用链，有的**算完了结果没人接**。
这两种情况源码都是"有引用的"——静态审计看不见。

所以本轮换了个测法：**运行时探针 + 能力矩阵**。

## 2. 八条实证缺陷

每一条都给了现象、证据、根因、修法、复验方式。**没有一条是靠读代码猜出来的。**

### 缺陷 1｜单文件下行动建议整块缺席（最重）

**现象**：只给一份数据（最常见的用法）时，报告里「永久措施候选」「预防建议」两节
从来不出现。同一份涂布数据，追加一个卷绕文件后，永久对策出 5 条。

**证据**：
```
单文件    lateral=缺   permanent=缺   preventive=缺   crossprocess=缺
双文件    lateral=有(0条) permanent=有  preventive=有   crossprocess=有
```

**根因**：`lib/pipeline.py:1514` `if len(tables) > 1 and chosen_proc:` ——
`permanent_actions` / `preventive` 整段写在这个跨工序分支里。
这两块其实**不依赖跨工序对齐表**：前者查知识库里该缺陷已验证的对策，
后者看参数与目标的相关性强度。用本工序的归因就能算。

**修法**：
- `lib/actions.py` 新增 `self_trace_from_result()`，用 `strong_pairs` 构造"只有本工序"的输入；
- `lib/pipeline.py` 在 DOE 之后加兜底：`if not result.get("permanent") and chosen_proc:`；
- verdict 写 **「仅本工序（未做跨工序追溯）」**，不借用「本工序主导」——
  后者是"查过上游并排除上游"的意思，与"没查"是两件事。

**第一次修错了位置**：补丁原放在第 6b 节旁边（1560 行），但 `strong_pairs`
在 1981 行才生成，`_self_tr` 恒为 `None`，静默不生效。
——这正是"模块写好了但接在错误的时机"，读代码看不出来，只有跑一遍才暴露。

**复验**：`scripts/selftest.py::test_cross_module_coherence` + 审计规则 #85（2 变异体）。

### 缺陷 2｜仓库自带示例配自己的示例数据，一跑就崩

**现象**：
```
fde_run.py analyze --input examples/08_跨规格版本数据.csv \
                   --spec examples/08_规格版本.json
→ AttributeError: 'list' object has no attribute 'get'
→ 【本轮未通过】已生成运行诊断
```
一份报告都出不来。而 1087 项自检全绿。

**根因**：规格条目有两种合法形态——单版本 `{"lsl":0,"usl":300}`（dict）
和多版本 `[{...A...},{...B...}]`（list）。`pipeline.py:324` 写 `ov.get("lsl")`，
假设它一定是 dict。第二处 `1671` 同样。

**为什么自检没抓到**：`test_pipeline` 只调 `PL.analyze([csv])`，**从不带 `--spec`**。
08 这条规格版本化路径从来没被任何测试走过。

**修法**：
- `lib/preprocess.py` 新增 `spec_entry_bounds()` 统一归一化（dict → 1 条，list → 每版 1 条）；
- `pick_target` 按"最可能超规的那一版"选目标列（宁可多看一列）；
- Cpk 分段前的兜底分支：多版本却未分段时**不挑一版冒充全部**，
  取最宽包络并在 warnings 里说明"只作参考"；
- 自检新增「示例的外部配套文件必须也跑一遍」——判据不是"记得测 08"，
  而是"示例自带的输入必须能喂进它自己"。

**复验**：规格版本化实测出 2 段（A 段 60 行 / B 段 60 行），审计规则 #86（2 变异体）。

### 缺陷 3｜清洗检出了 42 个离群点，但一个字都不说

**现象**：E07 小厂脏数据，`clean.rows_in=120`、`rows_out=120`，
`outliers` 里赫然记着 `{"NG_CNT": {"method":"mad","count":42,...}}`，
而 `clean.actions` 和 `clean.cleaning_log` 都是**空数组**。
使用者看到"120 行进、120 行出"会以为没做过任何处理。

**根因**：`lib/preprocess.py` 的离群点分支只写 `rep["outliers"][c]`，**从不写 `rep["actions"]`**。
物理量程分支写了、单位错配分支写了，唯独最常见的离群点分支没写。

**修法**：检出后追加 action，措辞区分"标记"与"删除"：
> 列 'NG_CNT' 检出 42 个离群点（mad 法，界限 [0.3115, 13.6549]），**仅标记未删除**

**复验**：自检「检出离群点时清洗动作里有对应叙述」。

### 缺陷 4｜"为什么没有根因"指错了方向

**现象**：E07 的 `data_sufficiency.reason` 说
> 数据已够（42 个有效样本），但没有任何候选拿到数据支持——**真因可能不在知识库收录范围内**

而真实原因是：10 列里只映射上 1 列（`T1/T2/Load/Thk/RH` 全是自定义列名）。
用户照着"补知识库"去干，会白干一轮。

**根因**：`lib/rootcause.py::_data_sufficiency` 把两种完全不同的处境
（① 候选数为 0 ② 候选有但验不了）共用一句理由。

**修法**：拆成两个分支，各自给正确动作：
- 候选 0：「先看报告里的列映射明细再补数据」（不是补知识库）
- 候选有但验不了：「有候选、但验不了」，并报出候选条数（新增 `n_candidates` 字段）

**复验**：实测 dirty 场景现在报 `n_candidates=6`，理由是"有候选、但验不了"。

### 缺陷 5｜EWMA 换了方法，却不告诉人代价

**现象**：报告里只说"已改用 EWMAST"，不说这个 λ 下误报率多少、多大偏移能检出、平均迟报几点。

**根因**：`lib/pipeline.py::_brief()` 只挑 `method/n_alarms/lambda/L`，
`performance_note` 与 `note` 被整个丢弃。

**修法**：`_brief` 一律带出 `performance_note` / `note`——
它是读者判断**能不能信这张图**的唯一依据。

### 缺陷 6｜8D 缺 D2、D4 没验证，报告照出

**现象**：`eightd.render_8d` 返回了 `missing_d2`（11 项必填未填）与 `d4_ok=False`，
但 `pipeline` 只用了 `signoff` 和 `d2_filled`，两条结果无人读。
报告照出、结论照给，客户一问就露。

**修法**：升进 warnings：
> 8D 的 D2 还有 11 个必填项未填（什么异常、发生工序、设备/通道/工位、首次发现时间、谁发现）：在补齐之前，这份 8D 的问题描述是不完整的
> 8D 的 D4（根因验证）未通过：根因尚未被数据或小批试验确认，此时的 D5/D6 只是候选措施

---

### 缺陷 7｜预防措施四个参数全废，涂布和焊接拿到同一份建议

**现象**：`actions.preventive(trace_result, table, target_col, kb, process)`——
后四个形参**一个都没读**。于是任何工序拿到的预防建议都一模一样，
`PREVENT_TEMPLATE` 是写死的 3 条通用话。

**修法**：
- `process` → 查知识库定位工序名，templates 首条变成「**工序：极片涂布**——请写进该工序的工艺卡」；
  工序 key 不存在时明确报「知识库里没有该条目」，不静默给通用版；
- `kb` → 优先用调用方传入的那份（租户覆盖后的版本），不传才自读；
- `table`/`target_col` → 算目标列当前在窗口的位势，新增 `target_position`；
- 无好件/坏件对比数据时**不再默认"偏高"**（原实现 `0 < 0` 恒假 → 一律输出"偏高"，
  等于替现场编方向），改为"收严还是放宽需现场确认"。

### 缺陷 8｜横向排查清单与缺陷无关

**现象**（上一轮修，本轮验证有效）：
`lateral_plan(table, target_col, defect, current_process)` 收了 `defect` 与
`current_process` 却从不读 → 「焊接不良」与「面密度超差」拿到**同一份**清单。

**现状验证**：
```
虚焊    -> 清除证据
隐裂    -> 上游追溯 + 清除证据
功率衰减 -> 上游追溯 + 清除证据
无缺陷  -> 走通用
```

## 3. 模块触达实测（运行时探针）

`python scripts/dataflow_audit.py --all`，7 个用例合并：

```
收集  369,969 次 ｜ 清洗 2,850,214 次 ｜ 计算 7,397,126 次
分析 3,322,379 次 ｜ 转发 33,893 次 ｜ 报告 545,014 次 ｜ 判定 2,170 次
```

七个环节**全部有模块承担**，没有空缺环节。12 个"零调用"模块逐个核过：

| 模块 | 判定 |
|---|---|
| `doe` | 探针传了 `do_doe=False`，属探针偏差；CLI 默认开 |
| `specver` | 需要 `--spec`，场景未传（缺陷 2 修完后已能触发） |
| `reliability` `fmea` `process_window` `toolmatch` `recipe` `defectchar` | 独立子命令（`fde_run.py reliability` 等），不在 analyze 链上，**设计如此** |
| `views` `status` `ingest` | 需要 `--view` / 在 analyze 之外的入口被调用，**不是孤岛** |

> 这张表的意义：**不能把"未触达"当"孤岛"**。第一版探针把 12 个都报成孤岛，
> 逐个核下来全是场景没覆盖，只有 `actions` 是真断链。判据不做这层区分，
> 就会拿着一张 12 条的清单去修 11 个不存在的 bug。

## 4. 存量脱节：125 → 75

门禁第 9 步的棘轮基线从 **125 条降到 75 条**。构成如下：

| 类 | 原 | 现 | 说明 |
|---|---|---|---|
| A 孤儿能力 | 1 | 1 | `spc.auto_chart` 仍未被主流程调用（待接：子组/属性数据选图） |
| B 参数收了不用 | 61 | 54 | 11 条协议形参（`__exit__` 的 `exc_type/tb`、`setprofile` 回调的 `arg`）已分类；真修 `preventive` 4 参、`lateral_plan` 2 参 |
| C 产出无消费者 | 62 | 21 | 62 条统计量发布字段（`df1/df2/resid/power/...`）已分类；真修 `performance_note`、`insufficient_reason`、`missing_d2`、`d4_ok`、`self_only` |
| D 静默空返回 | 1 | 1 | `spc.detect_shift_segments` 返回 `[]` 是正确语义（已白名单说明） |
| E 死 CLI 参数 | 0 | 0 | 上一轮已清零 |

**"分类"不是"放过"**：审计器会把分类条数与类别一并打印，静默排除是被禁止的。
但必须承认——**真正修掉的只有约 10 条，其余 50 条是"本就不是缺陷"**。
把这件事说成"降到 75 条"，比说"修好了 50 条"诚实。

剩余 21 条 C 类里仍有真断头路（已列入下一轮）：
`kbstore.sync → locked_out`（同步被锁无人读）、
`rootcause.rank_root_causes → weights_validation_status`（权重校验状态无人读）、
`quality_guard.negative_verdict → strongest_process/strongest_condition`。

## 5. 这一轮新增的机器约束

| 机制 | 位置 | 防的是什么 |
|---|---|---|
| 能力矩阵 | `scripts/capability_matrix.py` | "某能力在某类数据上到底出不出东西"——7 场景 × 20 项，一跑就知道 |
| 数据流探针 | `scripts/dataflow_audit.py` | "这次分析走了哪条路"——模块触达 + 七环节覆盖 |
| 审计规则 #85 | `scripts/fde_run.py` | 行动建议不得只挂在多表分支（2 变异体） |

规则 #85 第一版判据打偏了两次：
先报 SKIP（`actions.py` 没进 `AUDIT_FILES`，变异注不进），
补了 `AUDIT_FILES` 后报 FAIL（判据查 pipeline 的兜底块，而变异打在 actions 上）。
**SKIP 比 FAIL 危险**——FAIL 告诉你有事，SKIP 让你以为门禁是好的。

## 6. 诚实结论

1. **各模块"自我感觉良好"是有制度原因的**：单测验的是"函数内部对不对"，
   而最容易复发的缺陷坏在函数之间。1087 项自检全绿，同时 `--spec` 一跑就崩。
2. **"能跑"不等于"协同"**：`actions` 三块能力单测全过、双文件时也真出结果，
   但在最常见的单文件用法下整块不执行。这类缺陷只有**按用法矩阵实跑**才能发现。
3. **修对位置比修对代码更难**：缺陷 1 的补丁第一版放在错误的时机（`strong_pairs`
   还没生成），代码本身没错，就是静默不生效。
4. **不用真实用法跑一遍，"修好了"就是自评**。
