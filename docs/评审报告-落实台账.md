## 二、报告里两条判断与实际不符（如实记录，没有照着做）

1. **「5 万行封顶」不成立。** 实测 6 万行（2.4 MB）可跑完，耗时 51.8 s，
   代码里没有任何行数/体积截断。真实痛点是**每次全量重算**与**多批次人工切分**，
   P2-1 因此做的是摄入层（目录批量 / 去重 / 游标），不是去"提高上限"。
2. **「许可密钥功能」条款描述了一件不存在的事。** 软件里没有任何授权校验代码，
   留着那条只会让条款与代码事实不符。处置是删条款（P2-3），不是去写一套校验。

## 四、下次接评审报告的固定动作（本轮踩过才固化）

1. **先复现一条最关键的**，立刻改代码；不要连续三条以上探索命令而不动生产代码。
2. 报告的每一条判断都要**先验证再执行**：能复现的改，复现不了的如实标（见第二节）。
3. 新规则**首跑必出误报**；降噪后必须注入真缺陷复验（`audit --selftest`）。
   反向验证出现**跳过**比失败更危险——那意味着这条规则从没被验过。
4. 判据要落在**动作/赋值**上。自查法：把要防的那行删掉，规则还判过吗？还判过＝判据停在字样层。
5. 文档与代码不一致也算缺陷：文档引用的章节、档位、数量要能被机器核（见 P3-1 的验收方式）。
