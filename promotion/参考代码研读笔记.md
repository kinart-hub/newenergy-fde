# 参考代码研读笔记：pandas 版 FDE 分析流程

> 对象：`examples/pandas_reference/fde_pandas_reference.py`（258 行，用户提供）
> 读法：**逐行读，每条先问「这段代码替使用者解决了什么问题」，再问「我们有没有」**。
> 不是挑错清单——挑错清单是上一轮在 APQP 项目里学偏的做法，这次不重复。

## 0. 一句话结论

这份代码**工程价值不高（有致命 bug，见第 2 节），但产品直觉很强**。
它最值得学的不是统计，而是**三件"为使用者着想"的小事**：

1. 所有能改的东西放在**顶部一块配置区**，不散落；
2. 流程切成**编号阶段**，每阶段**留一行日志**，出错知道错在哪；
3. 失败时**不是什么都不给**，而是给一份写着报错信息的文件。

这三件，主线引擎**一条都没做到位**。这是本次要补的。

**"你要改的东西都在这一块，别的地方不用动。"**
这是可发现性（discoverability）设计——不需要读 258 行代码就知道能调什么。

**我们现状（已核查）**

| 参数 | 位置 | 使用者能否找到 |

### 1.3 统一前缀埋点日志（L156, 169, 170, 177, 195, 210, 221, 225, 237）

```python
print(f"【FDE Phase3日志】开始读取输入文件: {input_file_path}")
print(f"【FDE Phase3日志】原始数据读取完成 | 总行数:{df_raw.shape[0]}, 总列数:{df_raw.shape[1]}")
print(f"【FDE Phase3日志】原始列名: {list(df_raw.columns)}")
```

**为什么值得学** 三点：

- **统一前缀** `【FDE Phase3日志】` → 使用者可以直接 `grep "【FDE"` 从几千行输出里捞出进度
- **打印原始列名** → 这一条尤其专业。中文 CSV 的表头经常带 BOM、全角空格、
  合并单元格残留，90% 的"读不到数据"其实是列名对不上。把列名打出来，
  使用者自己一眼就能看出来
- **行数前后对比**（清洗前 180 → 清洗后 180）→ 让"数据被过滤了多少"变成可见的量

**我们现状（已核查）**
`lib/pipeline.py` 全文只有 **6 处 print**，且都是错误/提示，不是阶段埋点。
使用者跑完只看到：

```

```

2.1 秒里干了什么、读了多少行、识别成哪道工序——**全不知道**。

**怎么吸收** → 任务 #60。

### 1.4 空数据显式报错 + 排查清单（L172–173, L196–197）

```python
if df_raw.empty:
    raise ValueError("原始上传文件读取结果为空！检查文件、表头、合并单元格、文件损坏")

if df_clean.empty:
    raise Warning("⚠️工艺过滤后数据为空，请检查筛选条件，参数过滤把所有数据剔除")
```

**为什么值得学**
这是整份代码里**最站在使用者立场的一行**。它没说 "EmptyDataFrameError"，
而是给了**四个排查方向**：文件 / 表头 / 合并单元格 / 文件损坏。
使用者拿到报错知道下一步干什么。

第二个更细：**区分"读进来就是空的"和"过滤完才空的"**——
两种情况的排查路径完全不同，报错里分开写，是真正理解现场的人写的。

**我们现状**
`lib/pipeline.py` 全文仅 `sys.exit(1)` 一处错误出口，无面向使用者的排查指引。

### 1.5 产物落盘后自检（L236–239）

```python
file_size = os.path.getsize(TMP_OUT_PATH)
print(f"【FDE Phase3日志】输出多Sheet文件写入完成，文件字节大小: {file_size}")
```

### 1.6 异常兜底仍产出可读文件（L243–249）

```python
except Exception as e:
    err_msg = f"【FDE Phase3异常】{str(e)}"
    print(err_msg)
    err_df = pd.DataFrame([[err_msg]], columns=["FDE运行报错信息"])
    err_df.to_excel(TMP_OUT_PATH, index=False, engine="openpyxl")
    return TMP_OUT_PATH
```

**为什么值得学**
**失败了也给一个文件，文件里写着失败原因。**
这个设计的潜台词是：使用者不一定盯着屏幕，可能是挂在那儿去干别的了。
什么都不产出，等于白等。

对比我们：分析失败时 `sys.exit(1)`，屏幕上打一行 ERROR，然后什么文件都没有。

### 1.8 编码兜底 utf-8-sig → gbk（L159–163）

```python
try:
    df_raw = pd.read_csv(input_file_path, encoding="utf-8-sig")
except:
    df_raw = pd.read_csv(input_file_path, encoding="gbk")
```

**为什么值得学**
中文 CSV 的真实痛点：导出方可能是 utf-8、utf-8-BOM、GBK 三种之一。
先试带 BOM 的 utf-8（能自动吃掉 BOM），失败退 GBK。

**缺陷**：`except:` 裸捕获会连 `KeyboardInterrupt`、`MemoryError` 一起吞掉，
使用者 Ctrl+C 都停不下来。应写 `except UnicodeDecodeError:`。

**我们现状** 主线 `lib/preprocess.py` 有编码探测（支持 utf-8-sig / gbk / gb18030 等），
**这条主线也已赢。**

## 2. 参考实现自身的缺陷（实测证据，非推断）

> 这几条**不是挑刺**，是"如果照抄会把什么带进来"的风险清单。
> 每条都有实测命令和实测输出。

| # | 行号 | 问题 | 实测证据 | 正确做法 |
|---|---|---|---|---|
| **1** | **L100** | **致命**：R4（连续 14 点交替）判定抛 `ValueError`，**整个分析必然走兜底分支** | 见下方实测 | `np.all(diff[1:] != diff[:-1])` |
| 2 | L51 | **死参数**：签名有 `usl=None, lsl=None`，函数体从未使用。使用者以为传了规格会判规格，实际只判 3σ 控制限 | 全文搜索无 `usl`/`lsl` 引用 | 要么用起来，要么删掉 |
| 3 | L197 | `raise Warning(...)` 是反模式，会被当成异常抛出而非告警 | Python 语义 | `warnings.warn(...)` |
| 4 | L38 | `from scipy import stats` 导入后从未使用 | 全文无 `stats.` | 删除 |
| 5 | L68–71 | 控制限用**全段数据**算（含异常点），异常把 σ 撑大、限变宽，最该报警的点反而落在限内 | 主线已用 Phase I/II 修掉 | 删除异常点后迭代建限 |
| 6 | L188,190 | 阈值 80~120 / 140~180 **硬编码**，换产品/换规格就要改源码 | 代码可见 | 规格由调用方传入 |
| 7 | L42 | `/tmp` 在 Windows 上不存在 | 路径语义 | `tempfile.gettempdir()` |
| 8 | L162 | 裸 `except:` 吞掉所有异常 | Python 语义 | `except UnicodeDecodeError:` |
| 9 | L207 | `len(df_clean)>=20` 时静默跳过 SPC，不报错也不提示 | 代码可见 | 显式记录"因样本不足跳过" |
| 10 | L144 | Pareto `cum<=0.8` 判 A 类：**把累计推过 80% 的那一项反而被划成 B/C**。例如累计 0.72→0.91 的那项是关键项却被标次要 | 逻辑推导 | 含跨阈值那一项进 A 类 |

### 缺陷 1 实测记录

```bash
python -c "
import numpy as np
diff = np.sign(np.diff(np.arange(14.0)))   # 复现 L98-100
print(diff.shape, diff[::2].shape, diff[1::2].shape)
all(diff[::2] != diff[1::2])
"
```

输出：

```
(13,) (7,) (6,)
ValueError: operands could not be broadcast together with shapes (7,) (6,)
```

**推论链**：L98 取 14 个点 → `np.diff` 得 13 个 → `diff[::2]` 取 7 个、`diff[1::2]` 取 6 个
→ 长度不等，numpy 广播失败抛 `ValueError`
→ 该函数要求 `n>=20`（L66），所以 `idx>=13` **必然发生**
→ 异常被 L243 的 `except Exception` 捕获
→ **这份代码只要样本量≥20，就一定只输出一张写着 `ValueError` 的兜底 Excel，
   永远不会产出真正的分析结果。**

> 这条很关键：它说明**"有阶段日志 + 有兜底"只是可观测性的一半**。
> 兜底把致命错误也兜住了，反而让 bug 藏了很久——使用者拿到的是"一份 Excel"，
> 看着像成功了。这正是我们吸收 1.6 时必须同时加的东西：
> **兜底产物必须带醒目失败标记，且退出码非 0。**

### 6.2 文档版里发现的**新缺陷**（比代码版更重要）

| # | 位置 | 问题 | 严重度 |
|---|---|---|---|
| **B1** | `calc_process_capability` L167–168 | **`sigma_within` 与 `sigma_total` 都是 `data.std(ddof=1)`，两者完全相等** → 必然算出 `Cp == Pp`、`Cpk == Ppk` | **高** |

**为什么 B1 严重**：
Cpk 的定义要求**组内标准差**（短期波动），Ppk 要求**整体标准差**（长期波动）。
两者混为一谈时，若存在组间漂移/批次差异，整体 σ 会显著大于组内 σ，
于是 **Cpk 被系统性高估**——工艺能力看着达标，实际在客户处出问题。

主线引擎的做法（`lib/spc.py:497`）：
```python
so = sigma_overall or S.stdev(vals)   # 整体 σ
sw = sigma_within or so               # 组内 σ，由 x_mr / xbar_r 传入
```
且 `lib/pipeline.py:711` 实际调用时传了 `sigma_within=xc.sigma_within`。
**这一条主线赢，必须守住。**

### 6.3 文档里**真正值得抄**的三件事

#### ① `SPEC_DICT` + "上线前必须替换成产线正式规格"

它在配置区里用**注释明确写出替换义务**：
```python
# ========= 工艺规格USL/LSL（用户按需修改为产线真实规格）=========
SPEC_DICT = {"涂布厚度": {"USL":120, "LSL":80}, ...}
```
> 并在风险章节重申：`SPEC_DICT` 内 USL/LSL 为示例值，上线前**必须替换成产线正式规格**。

**这是"参数不固化"的落地范式**：默认值可以内置，但必须
① 集中在一处 ② 注释写明是示例 ③ 风险章节再提醒一次。
我们引擎 README 里应该也补这一条。

#### ② 角色适配表——明确"谁看哪个 Sheet"

文档里直接给出：
| 角色 | 看哪个 Sheet |
|---|---|
| 现场工艺 | 3_异常汇总（一眼看超差）、6_5Why（辅助排查）|
| 质量工程师 | 4_SPC + 4_1_CpCpk + 5_Pareto + 6_5Why（复盘/8D/能力评审）|
| 数据复盘 | 1_原始、2_清洗（导出 Minitab/JMP 二次分析）|

**这正是用户最新要求的核心**。它的价值在于：**不是给所有人一份报告，
而是告诉每个人"你的那部分在第几页"**。我们引擎目前缺这个索引。

→ 对应落地：`--view` 视角参数 + 报告开头加"你该看哪几节"导航表。

#### ③ 风险与边界说明单独成章

文档第四节「风险与边界说明」列了 6 条，包括：
- SPC 控制线基于样本 3σ，区别于产品规格 USL/LSL
- 5Why 是知识库辅助推理，**不能直接作为质量判定依据**
- 规格是示例值，必须替换
- 列名不匹配要改 `key_cols`
- 超大文件会 OOM

**这个习惯很好**：把"我这个工具在哪里会失灵"写清楚。
我们引擎有 `gaps` / `caveats`，但**没有一份集中的"能力边界清单"**。

→ 对应落地：README 增加「能力边界与不适用情形」一节。

**结论**：
- **专业深度**：主线明显领先（统计口径、分层、DOE、闸门、零依赖）
- **可用性设计**：参考实现明显领先（配置区、阶段日志、兜底、角色索引、边界清单）

**这正好印证了那句话——算法决定能不能用，视角设计决定有没有人用。**

接下来补"角色索引 / 边界清单 / 配置区"。

## 7. 第三轮：Phase4 —— 扩充的 5Why 知识库

> 用户又提供了 `fde_phase4_full.md`。本轮重点是 **5Why 根因知识库扩充**：
> 从 3 条（超差 / 涂布厚度超差 / 硅片厚度超差）扩到 **13 条**，
> 覆盖锂电（涂布、卷绕、注液、化成、分容）+ 光伏（硅片、电池片、组件 EL）。

### 7.1 参考实现 Phase4 的条目清单（13 条）

| 领域 | 条目 |
|---|---|

### 7.2 主线对应现状（实测）

主线 `knowledge/process_specs.json` 的 `defect_rootcause` 有 **15 条**：
面密度超差、针孔气泡、厚边、极片错位、隔膜褶皱、内短路、自放电超标、
容量一致性差、内阻偏高、TTV超差、隐裂、断栅、FF偏低、热斑、功率衰减

其中光伏相关 **6 条**：TTV超差(pv_wafer)、隐裂(pv_cell_el)、断栅(pv_cell_el)、

**条目数据结构对比**：

| | 参考实现 | 主线 |
|---|---|---|
| 结构 | 7 元组 `[Why1..Why5, 改善, 验证]` | dict：`process` / `likely_params` / `mechanism` / `verify_data` / `quick_checks` / `carry_over_from` / `clearing_evidence` |
| 可检索性 | 仅按缺陷名精确 key | key + 别名归一化 + 数据驱动识别 |
| 数据关联 | 无 | **有**（likely_params 指向实际数据列） |
| 可维护性 | 改字典 | `kb_manage.py` 入库 + 热换 + 租户隔离 |

**结构层面主线更强**：参考实现的 5Why 是纯文本查表，
主线每个条目挂着"候选参数 / 要验什么数据 / 现场看什么 / 上游是否带入 / 排除证据"。

### 7.3 但实测出一个**真实覆盖缺口**（本轮最重要发现）

拿 `examples/05_EL缺陷检测数据.csv` 的实际缺陷列名，逐条对主线的 15 个 key：

| 实际数据里的 EL 缺陷 | 主线知识库 | 参考实现 |
|---|---|---|
| 隐裂 | ✅ 有 | ✅ EL隐裂 |
| 断栅 | ✅ 有 | ❌ 无（只有「断栅」在光伏段未列） |
| **黑心** | ❌ **缺** | ✅ EL黑斑（同类异名） |
| **碎片** | ❌ **缺** | ❌ 无 |
| **虚焊** | ❌ **缺** | ✅ EL虚焊 |
| **脏污** | ❌ **缺** | ❌ 无 |
| **边缘漏电** | ❌ **缺** | ❌ 无 |

**结论**：主线在光伏 EL 高频缺陷上**只覆盖 2/7**。
光伏组件厂的质量工程师拿 EL 数据来跑，5 类高频缺陷给不出根因——
工具会静默降级成"机理未收录"。

这正是"没站在使用者立场"的代价：
**缺陷是有的、数据是有的，但知识库里没有他们车间里的叫法。**

### 7.4 参考实现 Phase4 值得吸收的三点

#### ① 「未匹配缺陷」兜底模板

```python
kb_item = ROOT_CAUSE_KB.get(defect_name, ROOT_CAUSE_KB["未匹配缺陷"])
```
兜底条目明确写出：*"知识库需要新增该缺陷条目"* + *"改善：现场开展专项 8D 分析…更新 5Why 知识库"*

**价值**：把"我没收录"从静默失败变成**可行动提示**。
使用者知道下一步该干什么（补知识库），而不是以为工具坏了。

→ 主线现状：`info.get("mechanism", "机理未收录")` 有兜底，
但**没有告诉使用者可以怎么补**。这是差距。

#### ② 风险章节**主动坦白自己的弱点**

第四节第 7 条（本轮新增）：
> *5Why 匹配为**精确字符串匹配**，MES 导出缺陷文字必须和知识库 key 完全一致；
> 后续可升级模糊匹配*

**这个习惯极好**：把"我在哪里会失灵"写进交付物，
而不是让使用者在现场撞上去才发现。

→ 主线 README 应补「能力边界与不适用情形」。

#### ③ 知识库条目自带「改善措施 + 验证方法」

不只给 Why1~Why5，还带**改善方向**和**验证方法**。
使用者拿到的是"根因 + 怎么改 + 怎么验证"三件套。

→ 主线 `quick_checks` 相当于验证方法，
但**改善措施**是 `improvement_library.json` 单独维护的（122 条 param，但 improvement_library 只有 2.6KB）。

### 7.5 参考实现 Phase4 仍然存在的缺陷（与前两轮同源）

| # | 问题 | 说明 |
|---|---|---|
| 1 | **R4 广播错误未修** | 源码仍为 `all(diff[::2] != diff[1::2])`，7 vs 6 → 必然 ValueError |
| 2 | **sigma_within == sigma_total** | 仍都是 `data.std(ddof=1)` → Cpk 必然等于 Ppk |
| 3 | **控制限仍用全段数据** | 未做 Phase I/II 分离 |
| 4 | **5Why 是纯查表，无数据验证** | 不关联实际数据的相关性证据 |
| 5 | **`raise Warning()` 未改** | 仍是反模式 |
| 6 | **`from scipy import stats` 未删** | 仍是死导入 |
| 7 | **`usl/lsl` 仍是死参数** | 签名有、函数体不用 |
| 8 | **Pareto 不做分层** | 只统计缺陷类型，不按设备/班次/批次钻取 |
| 9 | **知识库硬编码在源码** | 改一次要动代码，且无租户隔离 |
| 10 | **5Why 的 Why5 是措施不是原因** | 如"建立校准与点检制度"属于对策，经典 5Why 误用 |

> 第 10 条值得单独说：5Why 的每一层 Why 都应该是**原因**，
> 最后一层是**根本原因**。把"建立制度"写成 Why5，
> 逻辑上是把"对策"当成了"原因"，后续 D5 就无从推导。

### 7.6 三轮合起来的最终判断

| 维度 | 赢家 |
|---|---|
| 统计口径（Cpk/Ppk 分离、Phase I/II） | 主线 |
| 数据结构（参数关联、上游追溯、排除证据） | 主线 |
| 知识库可维护性（热换、租户隔离、入库工具） | 主线 |
| 分层能力（设备/班次/批次钻取） | 主线 |
| **缺陷覆盖广度（尤其光伏 EL 现场叫法）** | **参考实现** |
| 配置区可发现性 | 参考实现 |
| 阶段日志与兜底可观测性 | 参考实现（但兜底会掩盖 bug，主线已修正） |
| 角色索引 / 边界清单 | 参考实现 |

**一句话**：
> 主线的**深度**已经赢了，缺的是**索引口径**——
> 知识库用的是"数据列名"和"机理命名"，而现场用的是"车间叫法"。
> 同一个缺陷，工程师叫「极片起皱」，库里记「隔膜褶皱」，就断了。
>
> **补的方向不是重写引擎，是给知识库加一层"现场叫法 → 标准条目"的别名索引。**

### 落地时发现的、研读阶段没看出来的一件事

我在研读笔记里写「别名数据一直在库里但没被用」，落地时才发现**它比这更严重**：
`params[].aliases` 不只没被用，直接拿来用还会**引入回归**。

给「功率衰减」桥接 `param_key=pmax` 后，别名索引继承了 pmax 的别名
（`Pmax` / `功率` / `峰值功率` / `最大功率`），列名 `Pmax_STC(W)` 被识别成
「功率衰减」缺陷列 —— 目标列 == 缺陷列，共线排除整条失效，
E06 用例的 `co_linear_excluded` 从 `['CTM','Pmax',...]` 变成空。

**教训**：`param_key` 的语义不是「该缺陷对应的参数」，而是
**「该缺陷的计量列」**。对「功率衰减」这类由**结果指标漂移**定义的缺陷，
`pmax` 是被分析的目标量本身，不是缺陷计数列。
所以知识库要能区分这两种语义 —— 这是加了 `response_defect` 标记的由来，
也是第 24 条 audit 规则存在的原因。

这条恰好印证了第 4 节写的那句：**参考实现的优点是索引口径，但它的缺陷也在这里**
—— 它用 7 元组纯文本查表，根本没有「目标量 vs 缺陷量」这个维度，
所以永远不会遇到这个问题，也就永远不会解决它。主线的 dict 结构能表达这个区分。
