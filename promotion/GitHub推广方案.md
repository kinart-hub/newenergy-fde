## 0. 这套方案到底要解决什么

**不是涨 star。**

GitHub 在这个项目里的角色只有两个：**信任背书**（让人相信你真懂工艺）和
**分发枢纽**（一个链接就能把包交到对方手上）。真正的转化——试用、内网部署、
商业授权——都发生在私域（微信 / 邮件 / 企业内网）。

所以下面每一个动作都必须能回答三个问题，答不上来的动作不做：

1. 它带来**谁**（工艺工程师？质量经理？自动化集成商？）
2. 我怎么**联系上他**（进群？邮件？issue？）
3. 它离**授权或定制单**更近了一步吗

## 1. 定位一句话（所有平台统一口径，不要每次重写）

> 给锂电池 / 光伏工艺与质量工程师的**零第三方依赖**产线数据分析技能包：
> 上传检测设备导出的 CSV/Excel，直接产出**可对外发出**的工艺分析报告与 8D 初稿。
> 纯 Python 标准库，**内网离线可用**；以 AI Skill 或命令行两种形态使用。
> 它**不下发任何参数设定值**——结论与建议分离，未确审不得对外。

统一口径的理由：不同平台说不同版本，会让人怀疑是不是同一个东西，
也会让"零依赖 / 离线 / 不改参数"这三个最硬的卖点被稀释。

## 2. 90 天目标与度量

**北极星指标：有效使用者** = 真正跑过一遍、拿到过报告的人（不是 star）。

| 指标 | 今天（基线） | 30 天 | 60 天 | 90 天 | 怎么测 |
|---|---|---|---|---|---|
| Star | 0 | 30 | 100 | 300 | GitHub 页面 |
| Fork | 0 | 5 | 20 | 50 | GitHub 页面 |
| 克隆/周（唯一） | — | 20 | 80 | 200 | Insights → Traffic |
| 有效使用者 | 0 | 5 | 20 | 50 | 进群 + 发过数据的人 |
| Discussion / Issue | 0 | 5 | 15 | 40 | GitHub |
| 试用企业 | 0 | 1 | 3 | 8 | 邮件记录 |
| 商业授权线索 | 0 | 0 | 2 | 5 | 邮件记录 |

**关键动作**：README 与每篇文案里的联系方式统一带参数
（`?utm_source=github&utm_medium=readme` 之类），否则 90 天后你只能看到
"star 涨了"，看不出是哪个渠道带来的。

## 4. 仓库侧转化（Landing）：别人点进来 5 秒内决定要不要看下去

### 4.1 首屏必须有的四件事（缺一件就跑掉一半人）

1. **一句话定位**（第 1 节那句）
2. **一段 30 秒能跑通的命令**（复制粘贴即可，不要先读三页文档）
3. **一张成果图**（报告长什么样 / social preview）
4. **许可一句提示**（简短，详情感兴趣的人自己往下翻）

### 4.2 README 结构建议（现在需要调整的地方）

现在的结构是：**第 0 节许可在最前面**，篇幅不小。
许可重要，但放在首屏会劝退——第一次来的人还没看到你能干什么，
先被"你不可以做…"拦住。

建议顺序：

```
定位一句话 + 徽章
  ↓
30 秒跑通（命令 + 输出截图）
  ↓
它能干什么（痛点对照表）
  ↓
核心能力（简短）
  ↓
许可（完整保留第 0 节内容，位置后移）
  ↓
进阶用法 / FAQ
  ↓
联系与商业授权
```

### 4.3 仓库元数据（一次性设置，长期生效）

- **Description**（≤160 字符，中英各一版，见 §9）
- **Topics**（10 个以内，挑搜索量大的）：
  `lithium-battery` `photovoltaic` `spc` `cpk` `8d-report` `root-cause-analysis`
  `quality-engineering` `manufacturing` `process-capability` `python-stdlib`
- **Homepage**：指向 README 中的一个锚点或你的联系页
- **Social preview 图**：`assets/social-preview.png`，仓库 Settings 里上传

### 4.4 Release 规范化

每次发版都要写三段：**新增 / 修复 / 升级注意**。
Release notes 是你唯一能主动推送给 watcher 的渠道，别浪费在"update files"上。

### 4.5 降低提问门槛

- 开 Discussions，分类设为：`Q&A` / `需求` / `商业授权咨询` / `展示你的用法`
- Issue 模板两个：`缺陷报告`（要贴命令 + 输出）、`数据格式适配请求`（脱敏列名即可）

## 5. 内容矩阵：用内容换信任，不是用功能列表换 star

三类内容，每类解决一件事：

### A. 技术科普（建立"这人真懂"的印象）

| 选题 | 一句话角度 |
|---|---|
| Cpk 到底怎么用才有效力 | 用企业规格算和用行业典型值算，效力完全不同；没给规格就别说 Cpk |
| SPC 判异八条准则在产线上怎么落地 | 别只跑 X-bar 图，分层才是产线的常态 |
| 涂布面密度：为什么均值合格但良率掉了 | 方差与分层的故事 |
| EL 隐裂 Pareto 怎么做才有用 | 按设备/批次/班次分层后再排，不要一锅煮 |

### B. 案例复盘（转化最强）

> 一次不良率上升的定位全过程（**脱敏**）

结构固定：现象 → 数据 → 一步步怎么收窄 → 结论 → 教训。
结尾一句："想自己跑一遍，脚本在这里。"

### C. 立场与答疑（信任，也是差异化）

| 选题 | 为什么值得写 |
|---|---|
| 为什么不用 pandas / numpy | 零依赖不是偷懒，是为了企业端免 pip install——这是真实的部署约束 |
| 为什么选 Elastic License 而不是 MIT | 把商业逻辑讲清楚，比遮遮掩掩更能赢得尊重 |
| **AI 不会改你的参数设定值** | 这是安全声明，也是最强卖点：D5 只给方向不给设定值，未确审不得对外 |
| 客户数据为什么不入库 | .gitignore + 上架前隐私审计双保险，说给客户听是加分项 |

**节奏**：每周 1 篇 A 类，每两周 1 篇 B 类，C 类随需。

## 7. 商业化路径（四步，别跳步）

```
① 免费自用（GitHub 下载 / 技能市场安装）
        ↓  他跑通了，拿到报告
② 进群 / 邮件订阅（留下联系）
        ↓  他有真实问题
③ 试用：他发脱敏数据，我出报告（我出劳力，他出信任）
        ↓  他想在内网全员用
④ 内网部署 / 商业授权 / 定制工序包
```

- **免费**：个人与企业内部自用（Elastic License 允许）
- **收费**：对外托管服务（License 明确限制，需单独授权）、内网批量部署、定制工序与设备档案
- **定价锚点**（建议，不含税）：内网部署按年；定制工序/设备档案按项；托管服务单独谈

第 ③ 步是整个漏斗的关键：**免费出一次报告，成本是你一小时，回报是信任和一份真实案例。**

## 8. 合规红线（碰了会反噬）

1. **绝不自称开源**。Elastic License 2.0 是 source-available，不是 OSI 认证。
   说错一次，业内人会把你当成不懂许可的人。
2. **不承诺具体良率提升数值**。可以说"定位到根因"，不能说"提升 3%"。
3. **客户数据绝不入库**：`.gitignore` + `prepublish_audit` 双保险；
   案例必须脱敏，设备型号、批次、厂名全部替换。
4. **报告带"未确审不得对外发出"**——这是卖点不是 bug，要主动讲。
5. **第三方贡献必须先签 CLA**（`CLA.md`），否则将来无法统一变更许可。
6. 发群前先问群主；不做硬广；不发外链轰炸。

## 10. 复盘机制

每月固定一天做三件事：

1. 看 Insights → Traffic：哪个渠道带来人
2. 看 Discussion：被问最多的问题是什么 → 下个月的内容选题
3. 看"有效使用者"有没有涨 → 没涨就是渠道不对，不是内容不够

**指标不涨时先怀疑渠道，不要先怀疑内容。** 内容差的文章会掉粉，
内容好但发错地方的文章连数据都没有。
