# 使用者视角架构设计

> **本文要解决的问题**：newenergy-fde 现在是一个**算法很强、但没设计过"谁来用"**的工具。
> 统计口径、确审闸门、零依赖这些硬骨头都啃下来了，
> 但使用者拿起它之后的三件事没管：**他在哪一步会卡住、用完要拿什么去干活、出了问题怎么排查。**
>
> 本文按角色重做一遍需求分析，对照引擎现状逐条核查，给出缺口与落地路线。
> 所有"现状"结论均来自实际执行与代码核查，非推断。

---

## 0. 先说结论

按使用者立场重查一遍后，最扎眼的三个事实：

| # | 事实 | 证据 |
|---|---|---|
| 1 | **跑完不知道产出在哪** | 编排器打印 5 步 PASS 后结束，屏幕上没有任何产出路径；`result.json` 里有完整 `outputs`（md/html/xlsx/charts），但没被用起来 |
| 2 | **生成的 8D 录入卡没人知道** | `output/_ux_probe/8D_D2录入卡.md` 已落盘，但屏幕上没有"填写后回传 `--d2-card`"的引导。8D 闭环的关键一环，生成了却断了 |
| 3 | **生产主管最需要的东西完全没有** | 全库 grep `放行/隔离/挑选/处置/MRB`，零命中。分析结论里没有一句"这批货怎么办" |

这三条**都不是算法问题，是产品设计问题**。修起来零风险、纯增量。

## 1. 使用者画像：谁在用、在什么场景下用

按"**他们要决定的那件事**"来分，不按岗位名称分。同一个人在不同场景会切换角色。

### 1.1 五类使用者与他们的核心决策

| 角色 | 触发场景 | 要决定的那件事 | 时间压力 | 现有替代手段 |
|---|---|---|---|---|
| **工艺工程师** | 良率掉下去、客户投诉某参数 | 调哪个参数、验证区间取多少 | 小时~天 | Excel 透视 + 经验拍 |
| **现场技术人员** | 接到"去查一下 3 号机" | 现在去现场看什么、按什么顺序 | 分钟 | 纸笔 + 老师傅带 |
| **质量管理人员** | 客户要 8D、验货不通过 | 这份能不能发出去、证据够不够 | 天 | 手写 8D 模板 |
| **生产主管 / 班长** | 产出异常、货要出柜 | **这批放行 / 隔离 / 挑选** | 分钟~小时 | 拍脑袋、电话问 |
| **设备工程师** | 怀疑设备漂移 | 是不是设备的锅、哪一台哪个腔 | 小时 | 设备日志人工翻 |

### 1.2 各类使用者的真实约束（容易被忽略）

这些约束决定了"能不能用起来"，比功能列表更重要：

| 约束 | 具体表现 | 对设计的含义 |
|---|---|---|
| **不会写 JSON** | 工艺工程师看得懂报表，写不了 `{列名:{lsl,usl}}` | `--spec` 必须配"生成模板→填表→回传"路径 |
| **不一定盯着屏幕** | 现场人员点完去干活了 | 失败不能只打一行 ERROR，要落盘诊断文件 |
| **要能带走** | 现场没电脑，或只能拿打印件 | 关键产物要可打印（作业单） |
| **术语门槛** | Cpk / Nelson / MAD / 共线性 现场听不懂 | 需要术语速查或角色化措辞 |
| **对外要能发** | 客户不看 12 节长报告 | 需要客户版单页摘要 |
| **内网可能没网** | 装不了包 | 零第三方依赖（已守住，不动） |

### 2.1 逐角色对照

> ✅ 已有且够用｜⚠️ 有但不够｜❌ 缺失

| 角色需要 | 引擎现状 | 判级 | 缺口说明 |

| 参数角色区分（因子/指标） | 报告第 3 节输出"可调控因子 / 结果指标" | ✅ | 专业，DOE 选因子的前置 |
| 过程能力 Cpk | `lib/spc.py:497 process_capability` | ✅ | — |
| SPC 判异 | `spc.py:380 nelson_violations`，**默认 WECO(1,2,3,5)** | ✅ | 口径正确：全 8 条会虚警爆炸 |

| 根因定位 + 5Why | `lib/rootcause.py`，第 8 节 | ✅ | — |
| Pareto + ABC 分级 | `rootcause.py:170 pareto` | ⚠️ | 阈值 80/95 **硬编码**，不可调 |
| DOE 方案 | `lib/doe.py`，第 10 节，含备选设计 | ✅ | — |
| 8D 初稿 + 确审闸门 | `lib/eightd.py` + 红标 | ✅ | — |
| **产出路径提示** | 无 | ❌ | 见 §0 事实 1 |
| **8D 回传引导** | 条件未触发，无提示 | ❌ | 见 §0 事实 2 |
| **批次处置建议** | 无 | ❌ | 见 §0 事实 3 |
| **现场作业单（可打印）** | 仅 2 条通用 quick_checks | ❌ | 无方法、无判据、无记录栏 |
| **术语速查** | 无 | ❌ | — |
| **客户版单页摘要** | 无 | ❌ | 12 节太长 |
| **阶段日志 / --verbose** | 无（pipeline.py 仅 6 处 print） | ❌ | 2.1s 黑盒 |
| **失败诊断产物** | 无，仅 `sys.exit(1)` | ❌ | — |
| **可调参数清单** | 无 | ❌ | 80/95/1.33 都埋在代码里 |

### 2.2 一个具体例子：quick_checks 现在长什么样

实测 `output/_ux_probe/result.json`：

```json
"quick_checks": [
  "先按设备号/批次号/班次做分层，确认问题是全局还是集中在某一单元",
  "确认目标列「不良率(%)」的异常起始时间点，与该时段的工程变更做比对"
]
```

问题很明确：**方向对，但不可执行**。
现场技术员拿到这两句，不知道：去哪台设备看、用什么量具、测几个点、
什么值算异常、看完记在哪、下一步交给谁。

对比一份能用的现场作业单应该长这样：

| 序 | 检查项 | 位置/对象 | 方法 | 判据 | 实测 | 判定 | 异常处理 |
|---|---|---|---|---|---|---|---|
| 1 | 浆料固含 | 3号机供料罐 | 取样×3，烘干法 | 超出验证区间 → 异常 | ____ | □正常 □异常 | 停线，通知工艺 |

**差异不在内容深浅，在有没有替使用者把"下一步动作"写出来。**

## 3. 架构设计：一个引擎，五种视角，一个闭环

### 3.1 总体原则

> **算一次，看五种。**

不能让 5 个角色算 5 遍——结果必须一致，否则跨角色对不上就是灾难。
所以架构是：**计算层唯一，呈现层分视角**。

```
                    ┌─────────────────────┐
    输入 CSV/XLSX ──▶│   计算层（唯一）     │
    规格 --spec      │  lib/pipeline.py    │
                    │  清洗→判定→SPC→能力  │
                    │  →相关→Pareto→根因   │
                    │  →DOE→8D            │
                    └──────────┬──────────┘
                               │  result.json（唯一事实源）
              ┌────────────────┼────────────────┬──────────┐
              ▼                ▼                ▼          ▼
        ┌──────────┐    ┌──────────┐    ┌──────────┐  ┌────────┐
        │ 工艺视角 │    │ 现场视角 │    │ 质量视角 │  │生产视角│
        │ 参数/DOE │    │ 作业单   │    │ 对外摘要 │  │ 处置  │
        └──────────┘    └──────────┘    └──────────┘  └────────┘
              └────────────────┼────────────────┘
                               ▼
                    现场验证 → 回传 → 复算 → 结案
```

### 3.2 五种视角的产物定义

#### 视角 A：工艺工程师（默认，`--view process`）

**他要的**：调哪个参数、验证区间取多少、怎么排试验

| 产物块 | 内容 | 现状 |
|---|---|---|
| 参数优先级表 | 按证据得分排序，标注可调控/不可调控 | ✅ 第 8 节有 |
| 强关联参数 | r 值 + 显著性 | ✅ 第 6 节有 |
| 共线性剔除说明 | 谁被剔了、为什么 | ✅ 第 10 节有 |
| **建议验证区间** | **给区间不给设定值** | ⚠️ 缺 |
| DOE 方案 | 正交表/全因子 + 备选 | ✅ 第 10 节有 |

> **关键界限**：给"建议验证区间"，**绝不给"设定值"**。
> 理由：`lib/eightd.py` 已明确 D5 不含参数设定值——设定值只有现场验证说了算，
> 脚本代填会在客户审核时成为直接失分项。
> 区间是"去哪里试"，设定值是"答案"，这两件事必须分开。

#### 视角 B：现场技术员（`--view shopfloor`）

**他要的**：现在去哪、看什么、怎么测、什么算异常、记在哪

产物 = **现场作业单**（Markdown，可直接打印 A4）

```
┌────────────────────────────────────────────┐
│ 现场验证作业单                              │
│ 工序：极片涂布 ｜ 设备：3号机 ｜ 班次：乙班   │
│ 首要候选根因：浆料固含（得分 0.96）          │
├────────────────────────────────────────────┤
│ 检查项 / 位置 / 方法 / 判据 / 实测 / 判定   │
│ …（表格，每项一行）                          │
├────────────────────────────────────────────┤
│ 执行人 ______  日期 ______  复核 ______     │
└────────────────────────────────────────────┘
```

**这是当前最大的空白**，且是"最容易让现场觉得这工具真有用"的一块。

#### 视角 C：质量管理（`--view quality`）

**他要的**：能不能发、证据够不够、谁签字了

| 产物块 | 内容 | 现状 |
|---|---|---|
| 确审状态看板 | D5–D8 四道闸门逐项状态 | ✅ 有 |
| 不得对外红标 | 未确审时红标 | ✅ 有 |
| **客户版单页摘要** | 1 页，问题/范围/根因/对策/验证 | ❌ 缺 |
| 证据链索引 | 每个结论指向哪张表哪个数 | ⚠️ 散落 |

#### 视角 D：生产主管（`--view production`）

**他要的**：这批货怎么办

产物 = **批次处置建议表**

| 批次/时段 | 样本量 | 不良率 | 与基线的偏离 | 建议处置 | 依据 |
|---|---|---|---|---|---|
| B-2301 08:00-12:00 | 45 | 5.8% | +3.2pp | **隔离待判** | 超出验证区间 |

处置口径（三选一，脚本给建议不替人决策）：
- **放行**：在规格内且无判异
- **挑选**：超出规格但可 100% 检出
- **隔离**：超出规格且无法全检，或根因未明

> **风险提示**：处置建议属于**高风险输出**。一旦给出"放行"而后续流出不良，
> 责任归属会扯皮。所以设计上必须：
> ① 措辞是"建议"不是"结论"；② 必须带依据列；③ 未确审时同样带红标；
> ④ 记录"谁在什么数据上做的判断"。

#### 视角 E：管理层（`--view mgmt`）

**他要的**：损失多少钱、趋势向上还是向下、需要我拍板什么

一页纸：良率趋势 + 损失折算 + 待决策项（不超过 3 条）

## 4. 主动发现的问题清单（用户未点名）

> 这一节是自查结果。除第 0 节三条外，以下为扫描中额外发现的缺口。

### A 类：入口与可发现性

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| A1 | **双入口不一致**：`lib/pipeline.py` 是直连 CLI（无子命令），`scripts/fde_run.py` 是编排器（有子命令） | 实测：`python -c "...main()" ` 传 `analyze` → `error: unrecognized arguments: analyze` | 使用者照文档抄会直接报错，**第一次用就劝退** |
| A2 | `--help` 输出为英文 argparse 默认格式，16 个参数无中文分组 | `pipeline.py:2244–2268` | 现场人员看不懂 |
| A3 | `--spec` 要求手写 JSON，无模板生成 | 无相关命令 | 工艺工程师用不起来 → 退回硬编码 |
| A4 | 可调参数（Pareto 80/95、Cpk 1.33）无清单可查 | `rootcause.py:181,183`；`spc.py:549` | 违反"参数不固化"，且使用者不知道能改 |

### B 类：角色适配

| # | 问题 | 影响 |
|---|---|---|
| B1 | 单一输出，五种角色看同一份 12 节报告 | 工艺工程师嫌浅、现场人员看不懂、客户嫌长 |
| B2 | **无批次处置建议**（全库零命中） | 生产主管最需要的一环完全空白 |
| B3 | quick_checks 仅 2 条通用建议，无方法/判据/记录栏 | 不可执行、不能打印带走 |
| B4 | 无术语速查 | Cpk/Nelson/MAD/共线性 对现场是黑话 |
| B5 | 无客户版单页摘要 | 12 节报告客户不看，还要人工再摘一遍 |

### C 类：可观测性与兜底

| # | 问题 | 证据 |
|---|---|---|
| C1 | 流水线内部无阶段日志 | `pipeline.py` 全文仅 6 处 print，无阶段埋点 |
| C2 | 无 `--verbose` | 2.1s 完全黑盒，卡住不知卡在哪 |
| C3 | 失败无诊断产物 | 仅 `sys.exit(1)` + 一行 ERROR |
| C4 | 无产出落盘自检 | 可能产生坏文件而不知 |

### D 类：发现的一个真实 bug

| # | 问题 | 证据 |
|---|---|---|
| D1 | **参考实现 R4 判定必然抛异常**（非主线问题，但提示兜底设计要点） | 见研读笔记 §2 实测 |

> **D1 带来的设计教训**（这条比 bug 本身重要）：
> 参考实现有兜底，结果兜底把致命错误也兜住了——使用者拿到"一份 Excel"看着像成功，
> bug 藏了很久。**所以我们做兜底时必须同时满足三件事**：
> ① 兜底产物带醒目失败标记；② 退出码非 0；③ 兜底文件名明确含"诊断/失败"。

## 6. 风险与坑点（主动标注）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | **处置建议的责任风险** | 给出"放行"后流出不良，责任扯皮 | 措辞"建议"；必带依据列；未确审继承红标；留判断记录 |
| R2 | **建议验证区间被当设定值** | 使用者把区间中点当答案直接下发 | 报告显式标注"区间≠设定值，设定值须现场验证后确定" |
| R3 | **视角膨胀失控** | 5 个视角×12 章节 = 维护灾难 | 计算层唯一；视角层只做筛选与措辞；共用同一 result.json |
| R4 | **角色术语不统一** | 同一概念在不同视角叫法不同 | 建立术语映射表，单一事实源 |
| R5 | **过度设计** | 一次性铺 15 项容易烂尾 | 分三批，每批独立可交付、可回滚 |
| R6 | 兜底掩盖真实 bug | 见 D1 教训 | 兜底必带红标 + 非 0 退出码 |

## 7. 一句话

**算法决定了这个 skill 能不能用，视角设计决定了有没有人用。**

前者我们已经做到了（279 项自检、Phase I/II、四道确审闸门、零依赖）；
后者现在是空白——跑完不知道文件在哪、生成了录入卡没人知道、
生产主管问"这批货怎么办"答不上来。

补齐后者不需要动算法，风险低、见效快，且能让它从
「一份分析报告」变成「一套现场能跑起来的东西」。
