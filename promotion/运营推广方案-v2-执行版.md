**"成熟完善"的定义（本方案的总验收标准）：**

成熟 ≠ 功能多。成熟 = 同时满足三条：
1. 盲测 7 项反向指标全部达标（`holdout/盲测复核与v2.0整改规格.md` 的目标列）；
2. ≥3 份真实格式数据（非自造）跑通且不出静默错结论；
3. ≥2 个非开发者的真实工程师用过后，能向同事复述"这个报告可信、我下周还用"。

达不到这三条，推广动作全部降速——**把人拉进来看到错报告，比没人看伤害大十倍**。

## 1. 三线并行总路线

```
A 产品成熟线：v1.14.3 → v2.0（盲测达标）     ← 主线，决定"能不能推"
B 数据采集线：四路径并行，喂 A 线的别名库/设备档案  ← 决定"A 线改得动"
C 渠道运营线：30 天冲刺，冷启动找种子用户      ← 决定"有没有人用"
```

三线的耦合关系：C 线的种子用户反馈 + B 线的真实数据 → A 线的整改输入；
A 线每出一个达标版本 → C 线多一分敢推的底气。**前两周 C 线只做"轻触达"（发文章、进群观察），不做硬推广，等 A 线 P0 修完再放量。**

## 2. A 线：产品成熟路线（4 周，对应 v2.0 整改规格）

### 2.0 第零步（今天就做，10 分钟）

把当前未提交的 1463 行改动提交到独立分支并推送：

```bash
git checkout -b v2-fix-p0
git add -A && git commit -m "wip: v2.0 P0 整改进行中，先落盘备份"
git push -u origin v2-fix-p0
```

> 坑点标注：不要直接 commit 到 main——整改没验收前，main 必须保持"每个 commit 都能对外"的状态。

### 2.1 P0 整改排期（按 v2.0 整改规格 §4，验收指标钉死）

| 周 | 整改项（规格章节） | 验收标准（实测，不是"感觉好了"） |
|---|---|---|
| W1 | ① 证据门槛落在数据证据项（§4.1）② ID/时间/序号/坐标列过滤（§4.2/4.3）③ 目标列选择护栏，废弃"CV 最大兜底"（§4.3） | 伪相关居首率 = 0；低证据填 D4 率 = 0 |
| W1–W2 | ④ 别名误配治理：子串包含匹配收紧 + 别名库扩充（§3.1/3.2） | 错误工序率 ≤ 0.05（当前 0.33） |
| W2 | ⑤ 目标泄漏检测（§3.4）⑥ 批号前缀派生 + 批次×时间混杂检验（§4.4） | 错误目标率 ≤ 0.10；S2 类泄漏不再发生 |
| W2–W3 | ⑦ IV 数据 STC 温度修正（§3.6/4.6）⑧ 缺陷聚集检验（曝光加权 + Fisher/chi2，§4.5） | 知识库写了的，代码必须做到（制度缺口清零） |
| W3 | ⑨ 报告加输入文件哈希 + 运行清单（§4.7） | 每份报告可复现到具体文件与参数 |
| W4 | 全量回归：6 套对抗数据免提示重跑 | **top1 命中率 ≥ 0.70（当前 0.20），负例误报率 = 0** |
| W4 末 | 发 v2.0.0，Release notes 按"新增/修复/升级注意"三段式 | 这是第一次**可以放量推广**的版本 |

## 3. B 线：数据采集作战（与 A 线并行，本周启动）

按性价比排序的四路径（依据 `FDE-实用性验证方案.md` §2，本节把它变成动作）：

### 3.1 路径①：合成数据扩容（当天可做，已部分完成）

- 已有资产：`holdout/gen_holdout.py`（6 套对抗数据 S1–S6）、`examples/`（7 份示例）。
- 动作：每个目标工序补到 ≥3 套带已知真值的变体（不同噪声水平、不同"脏"法：多级表头/单位行/统计尾行/私有列名）。
- 交付物已建：`promotion/data-collect/`（用法见该目录 README）。

### 3.2 路径②：设备商与检测机构样本数据（重点攻，1–4 周）

要的不是数值机密，是**导出格式**——这东西敏感度低、对方给得起。

| 对象 | 要什么 | 触达方式 |
|---|---|---|
| 设备商应用/工艺支持工程师（先导、赢合、杭可、迈为、捷佳伟创、奥特维） | 一份任意客户（脱敏后）的设备导出 CSV 样例 | 行业群/展会名片/脉脉，话术见 `data-collect/话术模板.md` |
| 第三方检测机构（TÜV、SGS、CQC、鉴衡） | IV/EL 报告附带的原始数据样例 | 官网商务邮箱 + 行业会议 |
| 高校/研究院中试线 | 中试线产线数据（保密级别低，可谈合作署名） | 导师/校友链路 |

**目标**：30 天内每类工序拿到 ≥1 份真实导出格式。每份进来 → 建"设备档案"条目 → 跑一遍 FDE → 格式适配问题记 issue。

### 3.3 路径③：公开数据集（几天，顺手做）

NASA PCoE 电池循环数据集、NREL 光伏数据、国标 GB/T 31486 等标准里的示例表、论文附表。
定位：测格式多样性可以，测"算得对不对"不行（没有现场 ground truth）。

### 3.4 路径④：工厂 pilot（1–3 月，最终必做，只需 1–2 家）

- 来源：C 线漏斗里主动发脱敏数据来问问题的人（v1 §7 的第③步）。
- 结构：签 NDA → 对方发脱敏数据 + 口头告知已知真相 → 我 48h 内出报告 → 对方反馈"对不对、哪里不对"。
- 一份成功的 pilot = 一个 B 类案例复盘（脱敏）+ 一条商业授权线索。

### 3.5 路径⓪：JD 词频采集（每周 30 分钟，喂别名库）

- 工具已交付：`promotion/data-collect/jd_scan.py`（离线半自动：招聘网站手动复制 JD 存 txt，脚本出词频 + FDE 别名命中差表）。
- 目标：首期 50 份 JD → 产出行业词汇表缺口清单 → 直接送 `lib/preprocess.py` 别名库。
- 这是 `FDE-实用性验证方案.md §1` 判断的落地：**招聘网站是雷达不是水管**——只要名单和语言，不要数据。

## 5. 反馈闭环（运营数据如何喂回产品）

每个外部触点产出的信息，按类型归口：

| 反馈类型 | 归口 | 去向 |
|---|---|---|
| "我司设备导出长这样" | 设备档案 | `knowledge/devices/` 新条目 |
| "这个参数我们叫 XXX" | 别名库 | `lib/preprocess.py` 别名表，随下个版本发 |
| "报告这里结论不对" | **最高价值** | 复现 → 若是真缺陷进 v2.0 规格；若是数据歧义进对抗数据集 |
| "能不能接我们的 MES" | 商业线索 | 私域跟进，标 License 边界 |

## 7. 风险与红线（主动标注）

1. **本地未提交改动丢失**（概率中/损失大）→ §2.0 今天做。
2. **过早放量推广**：盲测 top1=0.20 的版本推给工程师 = 一次性烧掉信任，行业圈子小且互通。→ W4 前只做内容不做产品推荐。
3. **合规四条不变**（v1 §8 全文有效）：不自称开源、不承诺良率数值、客户数据不入库、报告"未确审不得对外"。另加第五条：**JD 采集只存公开文本，不爬个人信息，不留存联系方式**——采集的是"语言"，不是"人"。
4. **设备商数据陷阱**：设备商给的样例可能含其他客户残留信息，入库前过 `scripts/prepublish_audit.py`，不过不入。
5. **单人带宽**：老总每周新方向时间约 30h，本方案 W1–W4 需占用约 12–15h/周（其中 AI 可代劳约 60%：文案初稿、脚本、issue 分类、周报汇总）。超了就砍 C 线动作，**不砍 A 线**。
